Quickstart

1. Install the CLI 
git clone {source-repo-url}
cd apreg
go build -o apreg ./cmd/apreg

A go install-able release isn't published yet — build from source for now.

2. Create an account 
apreg signup --registry {registry-url}
apreg login  --registry {registry-url}

Your username becomes your publishing scope: plugins you publish live at @your-username/plugin-name.

3. Scaffold and publish a plugin 
apreg init my-plugin
cd my-plugin
apreg validate
apreg publish
4. Install someone else's 
apreg search postgres
apreg install @neondatabase/agent-skills

Installing plugins

Search by name, description, or keyword, then install by @scope/name. Installing fetches the tarball, verifies its sha256 checksum against what the registry recorded at publish time, and unpacks it into agent_plugins/<name> (override with --dir). 

apreg search context7
apreg view @upstash/context7          # inspect metadata without installing
apreg install @upstash/context7       # latest version
apreg install @upstash/context7@1.0.0 # a specific version
apreg install @upstash/context7 --dir vendor/context7

No signup required to search, view, or install — only publishing needs an account.

Publishing a plugin

apreg publish [dir] validates the directory locally (the same checks the server re-runs on receipt), packs it into a .tar.gz, and uploads it under your logged-in scope. The manifest's own name and version fields must match the URL the CLI publishes to — you never choose those independently of what's in plugin.json.

Publishing under someone else's scope is impossible by design: the server checks that your API token's owning username equals the scope you're publishing to, on every publish.

Plugin directory layout

A plugin is a directory containing a manifest and at least one of a skills/ folder or an mcp.json:

my-plugin/
├── plugin.json          # required manifest
├── skills/
│   └── my-skill/
│       └── SKILL.md      # required for each skill subdirectory
└── mcp.json              # optional MCP server config

plugin.json required fields per the Agent Plugins spec:

fieldrequirednotes
$schemayesmust be the official schema URL for the version you target
nameyes1–64 chars, lowercase alphanumeric/hyphen/period, no -- or ..
versionfor publishingmust be valid semver — the spec allows omitting it, but this registry requires one to publish (versions are how it addresses immutable releases)
description, homepage, repository, license, keywordsnoshown on the plugin's page and used by search

Run apreg validate in any plugin directory to check all of this locally before publishing.

Versioning

Versions are immutable, like npm: once @scope/name@1.0.0 is published, that exact content is permanent — publishing the same scope/name/version again is rejected. To ship a change, bump version in plugin.json and publish again. Installing without a version (apreg install @scope/name) resolves to the latest one published.

Accounts & security

Signup only needs a username, email, and password (8+ characters) — no email verification is required to start publishing, though you can confirm your address:

apreg verify-email {token}

Forgot your password:

apreg reset-password --registry {registry-url}

API tokens are shown once at login and stored in ~/.apreg/config.json. The registry rate-limits signup/login/publish per IP and locks an account out after repeated failed logins, independent of source IP.

REST API reference

The CLI is a thin client over this API — anything it does, you can do directly.

method & pathauthwhat it does
POST /v1/users—create an account
POST /v1/users/verify—consume an email verification token
POST /v1/tokensusername+passwordexchange credentials for an API token
POST /v1/password-reset/request—request a reset token
POST /v1/password-reset/confirm—consume a reset token, set a new password
PUT /v1/plugins/{scope}/{name}/{version}Bearer tokenpublish (raw .tar.gz body)
GET /v1/plugins/{scope}/{name}—plugin metadata + version list
GET /v1/plugins/{scope}/{name}/{version}—version metadata (latest is a valid alias)
GET /v1/plugins/{scope}/{name}/{version}/download—stream the tarball
GET /v1/search?q=—search plugins

Publish example, equivalent to apreg publish:

curl -X PUT "{registry-url}/v1/plugins/you/my-plugin/1.0.0" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @my-plugin-1.0.0.tar.gz

Self-hosting

AgentReg is free and open — there's no paid tier and nothing about it requires this particular instance. The whole thing (server, CLI, web UI, crawler) is one Go codebase with two moving parts: a metadata store (SQLite by default, or Postgres) and local-disk blob storage for tarballs. 

docker compose up --build

That runs the real production-shaped stack — the server backed by Postgres in a second container, both on persistent volumes. No external services, no account with us required, no license key.

Running your own instance is a completely independent registry — plugins published to one aren't visible on another. That's deliberate: self-hosting means your own namespace, your own users, your own data.
