Quickstart

1. Install the CLI 
git clone https://github.com/pkulkarnigit/agentreg.git
cd agentreg
go build -o krate ./cmd/krate

No go install-able release yet, so building from source is the only option for now.

2. Create an account 
krate signup --registry {registry-url}
krate login  --registry {registry-url}

Your username becomes your publishing scope: plugins you publish live at @your-username/plugin-name.

3. Scaffold and publish a plugin 
krate init my-plugin
cd my-plugin
krate validate
krate publish
4. Install someone else's 
krate search postgres
krate install @neondatabase/agent-skills

Installing plugins

Search covers name, description, and keywords. Install by @scope/name and it'll fetch the tarball, check its sha256 against what got recorded at publish time, and unpack into agent_plugins/<name> (or wherever you point --dir). 

krate search context7
krate view @upstash/context7          # inspect metadata without installing
krate install @upstash/context7       # latest version
krate install @upstash/context7@1.0.0 # a specific version
krate install @upstash/context7 --dir vendor/context7

Searching, viewing, installing: none of that needs an account. Only publishing does.

Every install is recorded in krate-lock.json in whatever directory you ran it from: the resolved version, checksum, source registry, and where it landed, regardless of --dir. krate list reads it back; krate uninstall deletes both the files and the entry. Reinstalling a plugin (e.g. to pick up a new version) replaces its directory outright rather than unpacking on top of it, so a file a new version dropped can't be left behind from the old one. 

krate list
krate uninstall @upstash/context7
There's no dependency resolution here on purpose. Plugins don't declare dependencies on each other, so there's nothing to resolve. This is the download-verify-unpack half of a package manager, not a build system.

Publishing a plugin

krate publish [dir] checks the directory locally first (the server re-runs the same checks on its end too), packs it into a .tar.gz, and uploads it under whatever scope you're logged in as. The name and version come straight from plugin.json: you don't get to pick something different at publish time.

You can't publish under someone else's scope, on purpose. The server checks your token's owner against the scope on every single publish. There's no override.

Plugin directory layout

A plugin is a directory containing a manifest and at least one of a skills/ folder or an mcp.json:

my-plugin/
├── plugin.json          # required manifest
├── skills/
│   └── my-skill/
│       └── SKILL.md      # required for each skill subdirectory
└── mcp.json              # optional MCP server config

plugin.json required fields per the Agent Plugins spec:

fieldrequirednotes
$schemayesmust be the official schema URL for the version you target
nameyes1–64 chars, lowercase alphanumeric/hyphen/period, no -- or ..
versionfor publishingmust be valid semver. The spec technically allows leaving it out, but we require it here: it's how the registry tells releases apart
description, homepage, repository, license, keywordsnoshown on the plugin's page and used by search

Run krate validate in any plugin directory to check all of this locally before publishing.

Versioning

Versions are permanent, same as npm. Publish @scope/name@1.0.0 once, and that's it. Try to publish that exact version again and it gets rejected. Want to ship a fix? Bump version in plugin.json and publish again. Leave the version off when installing (krate install @scope/name) and you get whatever's newest.

Accounts & security

Signup needs a username, email, and an 8+ character password. That's it. You don't need to verify your email to start publishing, though you can if you want to:

krate verify-email {token}

Forgot your password:

krate reset-password --registry {registry-url}   # prompts for username, then the token
krate reset-password --token <token>             # already have the token, skips straight to the new password prompt

Your API token shows up once, right after login, and gets saved to ~/.krate/config.json. Signup, login, and publish are all rate-limited per IP, and an account locks out after enough failed logins no matter where they're coming from.

REST API reference

Everything the CLI does against the registry (publish, install, search, view) you can do yourself against this API directly. krate list and krate uninstall are the exception: they only ever read and write krate-lock.json on your own machine, no network involved.

method & pathauthwhat it does
POST /v1/usersnonecreate an account
POST /v1/users/verifynoneconsume an email verification token
POST /v1/tokensusername+passwordexchange credentials for an API token

POST /v1/password-reset/confirmnoneconsume a reset token, set a new password

Self-reported and rejected if it's in the future; omit it and the server records the actual publish time, as normal.
GET /v1/plugins/{scope}/{name}noneplugin metadata + version list
GET /v1/plugins/{scope}/{name}/{version}noneversion metadata (latest is a valid alias)
GET /v1/plugins/{scope}/{name}/{version}/downloadnonestream the tarball

The only field on an already-published version that can ever change; everything else (checksum, manifest) stays permanent. Requires being logged in as a username in the server's KRATE_ADMIN_USERNAMES allowlist — empty, meaning nobody, unless the operator sets it.

Publish example, equivalent to krate publish:

curl -X PUT "{registry-url}/v1/plugins/you/my-plugin/1.0.0" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/gzip" \
  --data-binary @my-plugin-1.0.0.tar.gz

Self-hosting

There's no paid tier, and nothing here requires our instance specifically. It's all one Go codebase (server, CLI, web UI, crawler) sitting on two things underneath: a metadata store (SQLite or Postgres) and local disk for the actual tarballs. 

docker compose up --build

That's the real stack, not a stripped-down demo: Postgres in its own container, both on persistent volumes. No external services, no account with us, no license key to enter.

Your instance and ours don't talk to each other. Publish something here, and it won't show up on your own server, or anyone else's. That's the whole point of self-hosting: your namespace, your users, your data.
